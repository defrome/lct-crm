## Коротко

Заказчик не передал ни описание API (`OPEN-01`), ни перечень согласованных полей
JSON (`OPEN-04`). Поэтому сделан **работающий каркас приёма на демонстрационных
данных**: весь путь — забор → разбор → сопоставление → запись → постановка на
workflow → аудит — реализован по-настоящему и покрыт тестами. По допущению принята
только **форма входящего JSON**.

Когда контракт появится, меняется **один файл** — `backend/app/integrations/contract.py`.
Остальной код приёма не трогается.

| Что | Состояние |
|---|---|
| Забор данных по HTTP с пагинацией, токеном, таймаутами | Реализовано |
| Разбор и нормализация записей | Реализовано |
| Сопоставление с существующими вузами, вендорами, ПО, менеджерами | Реализовано |
| Запись через сервисный слой, upsert без дублей | Реализовано |
| Постановка новых карточек на workflow | Реализовано |
| Режим предпросмотра (dry-run) | Реализовано |
| История запусков, статистика, построчные замечания, аудит | Реализовано |
| **Соответствие полей внешних систем** | **Принято по допущению** |

## Как посмотреть, что оно работает

Источник без настроенного адреса работает на демонстрационных данных из
репозитория — специальной настройки не нужно.

```bash
# во что сейчас воткнуты интеграции и по какому соответствию полей
curl -s -H "Authorization: Bearer $TOKEN" \
  http://localhost:8000/api/v1/integrations/sources | jq

# предпросмотр: разбирает данные и сообщает, что изменится, ничего не записывая
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{}' http://localhost:8000/api/v1/integrations/lms/sync | jq .stats

# реальная запись
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"dry_run": false}' http://localhost:8000/api/v1/integrations/lms/sync | jq .stats

# повтор — дублей не появится
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"dry_run": false}' http://localhost:8000/api/v1/integrations/lms/sync | jq .stats

# история запусков с построчными замечаниями
curl -s -H "Authorization: Bearer $TOKEN" \
  http://localhost:8000/api/v1/integrations/syncs | jq
```

В dev-режиме вместо токена — заголовок `X-Debug-User: seed-manager`.

Демонстрационные данные подобраны так, чтобы показать каждое правило: точное
совпадение вуза, опечатку в названии, ненайденного менеджера, нераспознанную дату,
срок лицензии вне диапазона и запись без названия вуза, которая отбраковывается.

## Как подменить заглушку на реальный API

Порядок действий, когда контракт получен.

**Шаг 1. Описать реальные поля.** В `backend/app/integrations/contract.py` поправить
`LMS_CONTRACT` и `WEBSITE_CONTRACT`:

* `items_path` — где в ответе лежит массив записей (пустая строка, если тело
  ответа само является массивом);
* `cursor_path` и `cursor_param` — как листается выдача; `cursor_path=None`,
  если пагинации нет;
* `fields` — «поле CRM → путь в JSON», точками для вложенности: `university.name`,
  `data.0.title`;
* `contacts_path` и `contact_fields` — если контакты приходят вложенным массивом.

Если реальный ответ окажется сложнее, чем достаёт путь через точку (например,
записи разложены по нескольким ключам), менять нужно `SourceContract.records()` —
это по-прежнему один файл.

**Шаг 2. Прописать адреса.**

```bash
INTEGRATIONS_MODE=http
LMS_API_URL=https://lms.example/api/v1/interactions
LMS_API_TOKEN=...
WEBSITE_API_URL=https://site.example/api/v1/zayavki
WEBSITE_API_TOKEN=...
```

Источник, у которого адрес не задан, остаётся на демонстрационных данных даже в
режиме `http` — это позволяет переводить интеграции по одной.

**Шаг 3. Проверить предпросмотром.** Запустить `POST /integrations/{source}/sync`
с `dry_run: true` на боевой базе: запуск разберёт реальные данные, посчитает, что
изменится, и откатит все изменения. Смотреть `stats` и `messages`.

**Шаг 4. Удалить демонстрационные данные.** `backend/app/integrations/fixtures/*.json` и
тесты, которые на них опираются (они отмечены в `backend/tests/test_integrations.py`).

Чего менять **не** придётся: способ забора по HTTP, нормализацию значений,
сопоставление с существующими записями, правила записи, постановку на workflow,
аудит, эндпоинты и схемы ответов.

## Правила приёма

Те же, что у импорта Excel — намеренно: интеграция это та же задача, пришедшая
через другую дверь, и расхождение правил породило бы почти-дубликаты.

**Запись только через сервисный слой.** Используются `find_or_create` каталогов и
`InteractionService.upsert`, те же, что у импорта. Поэтому вуз из LMS и тот же вуз,
набранный в Excel, сворачиваются в одну строку. Это проверяется тестом: после
синхронизации LMS и сайта «МГТУ им. Н.Э. Баумана» существует в одном экземпляре.

**Ключ upsert — тройка «вуз + направление + продукт».** Повторный запуск не плодит
дубли, результат идемпотентен.

**Пустое значение — это «нет данных», а не «очистить».** Поле, которого нет во
входящей записи, не затирает заполненное значение в БД.

**Вуз сопоставляется сначала по внешнему идентификатору, потом по названию.**
Если точного совпадения нет, ищется похожее; при высокой близости выдаётся
предупреждение с подсказкой, но записи **не сливаются автоматически** — это решение
человека.

**Существующий вуз дозаполняется, но не перезаписывается.** Регион, ИНН и внешний
идентификатор проставляются, только если в БД они пустые.

**Ненайденный менеджер — предупреждение, а не отказ.** Поле «ответственный»
остаётся пустым, запись импортируется.

**Запись без названия вуза отбраковывается,** остальные применяются.

**Даты и срок лицензии** разбираются теми же правилами, что в импорте: `ДД.ММ.ГГГГ`,
`ГГГГ-ММ-ДД`, excel-serial числом; срок — целое 1–10, иначе предупреждение и пустое
поле.

**Новые карточки встают на workflow по умолчанию** — это требование `FR-06`
(«с последующим добавлением в существующий или новый workflow»).

**Каждый запуск пишется в аудит** действием `import` со сводной статистикой, плюс
обычные `create`/`update` по затронутым сущностям.

## Предпросмотр и транзакционность

Вся запись идёт внутри `SAVEPOINT`. При `dry_run: true` он откатывается, а запись
о самом запуске — она живёт во внешней транзакции — сохраняется, поэтому результат
предпросмотра можно посмотреть позже в истории.

Непредвиденная ошибка посреди синхронизации откатывает savepoint целиком и
переводит запуск в статус `failed` с текстом ошибки. Частично применённых данных не
остаётся.

Недоступность внешней системы — не исключение, а результат: запуск получает статус
`failed`, ошибка попадает в `error_message`, HTTP-ответ не пятисотит на ровном месте.

### Статистика запуска

| Поле | Значение |
|---|---|
| `total` | Сколько записей отдал источник |
| `to_create` / `to_update` | Что запуск решил создать и обновить |
| `created` / `updated` | Что фактически записано; **при dry-run всегда 0** |
| `skipped` | Пропущено из-за ошибок |
| `errors` / `warnings` | Число записей с ошибками и с предупреждениями |
| `contacts_created` | Заведено контактных лиц вузов |

## Из чего состоит

```
backend/app/integrations/
  contract.py       ← ЕДИНСТВЕННЫЙ файл под правку, когда придёт контракт
  sources.py        забор данных: FixtureSource и HttpJsonSource
  records.py        разбор записи во внутренний словарь + валидация
  ingest.py         оркестрация: предпросмотр, запись, статистика, аудит
  fixtures/         демонстрационные данные (удалить вместе с заглушкой)
backend/app/repositories/integration.py   доступ к истории запусков
backend/app/schemas/integration.py        контракты API
backend/app/api/v1/integrations.py        роутер
backend/app/models/integration.py         таблица integration_sync_runs
backend/tests/test_integrations.py        33 теста
```
