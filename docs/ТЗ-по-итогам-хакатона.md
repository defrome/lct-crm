# Техническое задание: дополнение по итогам хакатона

## 1. Назначение документа

Документ уточняет требования к CRM для работы с вузами, образовательными программами и заявками. Он составлен по материалам `Хакатон.md` и дополняет базовое ТЗ проекта. При противоречии с базовым ТЗ приоритет имеют требования заказчика, зафиксированные отдельно.

## 2. Цель доработки

Реализовать CRM, в которой сотрудники ведут заявки и взаимодействия с вузами по настраиваемым маршрутам (workflow), безопасно обрабатывают минимальный объём персональных данных, получают уведомления о событиях и могут работать из закрытого корпоративного контура с мобильных устройств.

## 3. Границы решения

### 3.1. Поддерживаемые группы контрагентов

Система должна разделять как минимум две группы:

| Группа | Описание | Требование к workflow |
|---|---|---|
| B2B | Вузы и иные образовательные организации | Отдельный настраиваемый маршрут работы с заявкой |
| B2C | Физические и юридические лица, не относящиеся к вузам | Отдельный настраиваемый маршрут работы с заявкой |

Для каждой группы необходимо назначать свой workflow. Этапы, переходы, уведомления и правила обработки заявок одной группы не должны неявно изменять процесс другой.

### 3.2. Персональные данные

В системе ведутся поимённые списки обучающихся, преподавателей и контактов. Базовый набор персональных данных необходимо ограничить:

- ФИО;
- рабочий или контактный email;
- служебные данные, необходимые для привязки к вузу, программе, расписанию или заявке.

Не следует собирать дополнительные персональные данные без подтверждённой деловой необходимости. Доступ к данным должен предоставляться только авторизованным пользователям в пределах их роли и области ответственности.

## 4. Функциональные требования

### 4.1. Управление workflow

| ID | Требование | Критерий приёмки |
|---|---|---|
| `H-WF-01` | Администратор может создавать workflow, этапы и разрешённые переходы между этапами. | Для нового workflow можно создать не менее двух этапов и настроить переход между ними. |
| `H-WF-02` | Workflow назначается группе B2B или B2C и применяется к создаваемым заявкам соответствующей группы. | Новые B2B- и B2C-заявки получают этапы из разных маршрутов. |
| `H-WF-03` | При изменении workflow система должна сопоставлять существующие активные заявки с этапами новой версии маршрута. | До сохранения изменения пользователь видит все затрагиваемые заявки и их целевые этапы. |
| `H-WF-04` | При удалении этапа необходимо обязательно выбрать этап, на который будут переведены все заявки, находящиеся на удаляемом этапе. | Удаление невозможно без выбора целевого этапа; после подтверждения все затронутые заявки переведены на него. |
| `H-WF-05` | Изменение структуры маршрута должно требовать явного подтверждения. | Перед сохранением показывается предупреждающий диалог с числом затрагиваемых заявок и необратимыми последствиями. |
| `H-WF-06` | Переименование существующего этапа доступно только администратору либо требует его подтверждения по принятой ролевой модели. | Пользователь без требуемого права не может сохранить новое наименование этапа. |
| `H-WF-07` | Все изменения workflow, сопоставления заявок и массовые переводы должны попадать в журнал аудита. | В журнале фиксируются автор, время, прежнее и новое значение, а также список или количество затронутых заявок. |

Для безопасной миграции этапов интерфейс должен предлагать целевой этап, предпочтительно следующий или предыдущий по маршруту, но окончательное решение принимает пользователь с соответствующими правами.

### 4.2. Работа с заявками и расписанием

| ID | Требование | Критерий приёмки |
|---|---|---|
| `H-REQ-01` | Карточка заявки должна содержать группу контрагента, текущий этап, ответственного, историю переходов и комментарии. | Пользователь открывает карточку и видит перечисленные данные. |
| `H-REQ-02` | Система должна поддерживать списки обучающихся и преподавателей, связанные с образовательными активностями. | Для активности можно просмотреть список участников с ФИО и email. |
| `H-REQ-03` | Система должна поддерживать сквозное расписание активностей по федеральным проектам и другим вариантам обучения. | В расписании отображаются связанные активность, период, вуз/проект и участники. |
| `H-REQ-04` | При переходе заявки по этапу пользователь может оставить комментарий. | Комментарий сохраняется в истории переходов с автором и временем. |

### 4.3. Уведомления

| ID | Требование | Критерий приёмки |
|---|---|---|
| `H-NOT-01` | Система должна поддерживать уведомления о переходах по workflow. | Для перехода можно включить правило уведомления адресата или роли. |
| `H-NOT-02` | Каналы уведомлений: email и интеграционный канал мессенджера. В качестве целевых мессенджеров предусмотреть Telegram и MAX. | Канал можно включить или отключить в настройках без изменения бизнес-логики workflow. |
| `H-NOT-03` | Должна быть опциональная проверка зависших заявок. Значение по умолчанию: более 14 календарных дней на одном этапе. | При включённом правиле ответственное лицо или его руководитель получает уведомление по настроенному каналу. |
| `H-NOT-04` | Получатель напоминания определяется настройкой: ответственный, руководитель ответственного, конкретная роль или назначенный пользователь. | Для правила можно выбрать хотя бы один из перечисленных способов адресации. |

Уведомления не должны блокировать сохранение заявки: при временной недоступности внешнего канала событие подлежит повторной отправке и регистрации в журнале.

### 4.4. Встроенный обмен сообщениями

| ID | Требование | Критерий приёмки |
|---|---|---|
| `H-MSG-01` | В сервисе должен быть реализован внутренний мессенджер или чат по рабочей карточке. | Авторизованные участники карточки могут отправить и прочитать сообщения в её контексте. |
| `H-MSG-02` | Доступ к переписке определяется ролевой моделью и областью доступа к заявке. | Пользователь без доступа к карточке не может открыть её переписку. |
| `H-MSG-03` | Сообщения должны хранить автора и время отправки. | Эти данные отображаются у каждого сообщения. |

### 4.5. Кэширование

| ID | Требование | Критерий приёмки |
|---|---|---|
| `H-CACHE-01` | Кэш применяется для ускорения повторного получения данных и ответа интерфейса. | Повторное обращение к кэшируемым данным не требует полного пересчёта или повторной загрузки из БД при валидном кэше. |
| `H-CACHE-02` | Кэш не должен быть самостоятельным офлайн-режимом редактирования с асинхронной синхронизацией изменений. | При потере связи пользователь не получает возможность редактировать и откладывать бизнес-изменения для последующей отправки, если такая функция не согласована отдельно. |
| `H-CACHE-03` | Для серверного кэша допускается Redis или KeyDB. | Конфигурация кэша вынесена из прикладной логики и может быть отключена. |

Кэширование локальных файлов, документов и страниц допускается только при соблюдении требований к защите персональных данных и политик закрытого контура.

## 5. Безопасность и инфраструктура

| ID | Требование | Критерий приёмки |
|---|---|---|
| `H-SEC-01` | Решение должно соответствовать применимым требованиям 152-ФЗ к обработке персональных данных. | Подготовлены описание обрабатываемых данных, ролевая модель, меры разграничения доступа и документация по развёртыванию. |
| `H-SEC-02` | Развёртывание выполняется в закрытом окружении без общего доступа к интернету. | Система сохраняет работоспособность при отсутствии исходящего интернет-доступа. |
| `H-SEC-03` | Разрешены только согласованные интеграции с LMS и CMS сайта. | Сетевые соединения ограничены согласованными IP-адресами, портами и протоколами. |
| `H-SEC-04` | Авторизация должна использовать корпоративный контур идентификации, в том числе Keycloak. | Пользователь входит через настроенный провайдер идентификации; права извлекаются из ролей или групп. |
| `H-SEC-05` | Должны вестись аудит значимых действий и журналирование ошибок интеграций. | Журналы доступны администратору и не содержат лишних персональных данных. |
| `H-SEC-06` | Решение допускается реализовать монолитным приложением. Модули должны включаться и отключаться через feature flags/toggles. | Отключение модуля не требует изменения исходного кода и не нарушает базовый сценарий CRM. |

## 6. Интерфейс и мобильный доступ

| ID | Требование | Критерий приёмки |
|---|---|---|
| `H-UI-01` | Веб-интерфейс должен быть адаптивным для мобильных устройств. | Основные сценарии: вход, просмотр списка, просмотр карточки, смена этапа и отправка сообщения доступны на ширине экрана 360 px и выше. |
| `H-UI-02` | Доступ с мобильного устройства должен быть совместим с корпоративной защитой, например VPN и клиентскими сертификатами. | Архитектура не препятствует прохождению трафика через корпоративный VPN/прокси и использованию TLS-клиентского сертификата при такой настройке контура. |
| `H-UI-03` | Любая опасная операция с workflow требует понятного диалога подтверждения. | Диалог явно описывает действие, последствия и возможность отмены до подтверждения. |

## 7. Документация и передача решения

| ID | Требование | Критерий приёмки |
|---|---|---|
| `H-DOC-01` | В продукте должна быть доступна офлайн-документация пользователя. | Руководство открывается без обращения к внешним интернет-ресурсам. |
| `H-DOC-02` | Должна быть подготовлена документация администратора по развёртыванию в закрытом контуре, конфигурации интеграций, ролей, кэша и уведомлений. | Документ содержит переменные конфигурации, требуемые сетевые правила и порядок запуска. |
| `H-DOC-03` | До защиты требуется предоставить возможность заранее подключиться к целевому контуру. | Команде переданы адрес, порядок доступа, учётные данные или иной согласованный способ подключения до демонстрации. |

## 8. Рекомендуемый минимальный состав демонстрации

1. Вход через Keycloak под пользователем и администратором.
2. Создание B2B- и B2C-заявок с разными workflow.
3. Переход заявки по этапам с комментарием.
4. Изменение workflow: переименование с проверкой прав, удаление этапа и обязательное сопоставление активных заявок.
5. Уведомление по переходу и пример напоминания для заявки, которая находится на этапе более 14 дней.
6. Чат в карточке заявки.
7. Адаптивная работа на мобильном экране.
8. Демонстрация запуска и документации в закрытом контуре.

## 9. Открытые вопросы для согласования

| ID | Вопрос | Предлагаемое решение до согласования |
|---|---|---|
| `H-OPEN-01` | Кто вправе переименовывать этап: только администратор или пользователь с подтверждением администратора? | Только администратор. |
| `H-OPEN-02` | Нужны ли Telegram и MAX оба сразу, и есть ли доступ к ним из закрытого контура? | Реализовать интерфейс каналов и включить доступные интеграции конфигурацией. |
| `H-OPEN-03` | Кто является получателем уведомления о зависшей заявке? | По умолчанию ответственный и его руководитель. |
| `H-OPEN-04` | Какие именно поля поступают из LMS и CMS, а также какие IP-адреса и порты разрешены? | Получить контракт API и сетевой перечень от заказчика до подключения интеграций. |
| `H-OPEN-05` | Какие действия в чате допустимы: только текст или также вложения и упоминания? | В первой версии поддержать текстовые сообщения; вложения согласовать отдельно. |
| `H-OPEN-06` | Требуется ли версия workflow как отдельная сущность с возможностью просмотра старой схемы? | Обязательно хранить аудит изменений; полноценное версионирование выделить в следующий этап, если не будет иной договорённости. |
